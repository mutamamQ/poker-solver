# Tree editing, nodelocks, and player profiles: bounded contract

## Evidence status and corrections

A BryantGPT worker produced the initial research draft. Parent read it in full and checked the public product articles and the repository's actual `GameState`/`CFRSolver` design. The draft was not implementation-safe:

- this repository has an implicit immutable game graph generated by `GameState.child`, not mutable UUID-bearing nodes;
- locking a physical node rather than an information set can leak hidden information and violate behavioral-strategy semantics;
- arbitrary UUIDs are neither deterministic nor stable across rebuild/serialization;
- adding an action with zero regret does not make the current policy uniform when existing actions have positive regret;
- reusing regrets after changing an action amount/subtree is not generally valid;
- the sample CFR recursions used two-player sign flips and reach updates incorrectly and did not match this repository's synchronous CFR;
- “single node = MinES” and “multi-node = MaxES” are not sound definitions of best-response behavior;
- the stated Kuhn oracle was underspecified, profile frequency thresholds were invented, and action-removal monotonicity need not hold for a player's equilibrium value when both players re-solve a changed game;
- predefined Fish/Nit/TAG/LAG values and several GTO Wizard capabilities were asserted without evidence.

The accepted design below uses deterministic information-set selectors, rebuilds edited games, distinguishes constraints from utility shaping, and validates actual EV separately.

## Verified public product semantics

GTO Wizard publicly describes:

- nodelocking as defining strategy locally at a decision point;
- profiles as persistent tendencies propagated across a game tree;
- four profile incentive categories: check, bet/raise, fold, and call;
- an example where a +5% pot calling incentive makes calls more attractive;
- incentives as virtual and excluded from displayed final EV;
- preflop configuration that can assign profiles to seats and lock specific ranges.

The Maniac article publicly gives `bet +6% pot`, `call +3% pot`, and `fold -6% pot` for that named product profile. It also warns that the simple profile does not distinguish bet sizes. These are product semantics, not a complete public algorithm or license to invent other preset values.

## Repository constraints

Current games implement `GameState`; children are generated on demand. `collect_infosets` enforces that every occurrence of an `InfoKey` has the same owner and legal action tuple. `CFRSolver` owns regrets and strategy sums keyed by `InfoKey`.

Therefore Phase 3 must not bolt mutable UUID nodes onto the current engine. The compatible identities are:

- `InfoKey`: strategy and nodelock identity;
- a deterministic public-history/configuration selector: tree-edit identity before rebuilding a game;
- `Action(kind, amount)`: exact action identity.

A selector must contain only public state needed to identify the edit target. It may include game/street, public board, public action history, acting seat, and configuration version. It must not include private cards when the edit is intended to apply across an information set.

## Tree editing

### Semantics

Tree editing changes the action-generation configuration for a deterministic public selector, then constructs a fresh root state and fresh solver. Supported edits are:

- replace the complete legal sizing set at a selector;
- add an exact legal action;
- remove an exact action while leaving at least one legal action.

“Change” is remove-old plus add-new followed by full validation and rebuild. Monetary actions use integer total-to amounts and the legality rules from the game-structure contract.

### Validation

Before accepting an edit:

1. the selector resolves to at least one reachable decision and all resolved occurrences belong to the same public decision class;
2. generated occurrences with the same `InfoKey` retain identical ordered action tuples;
3. action kinds and amounts are legal at every resolved occurrence;
4. there are no duplicate `Action` values;
5. at least one action remains;
6. a child can be generated for each action without violating stack, contribution, street, terminal, or perfect-recall invariants;
7. every existing nodelock targeting changed action tuples is rejected or explicitly remapped—never silently dropped.

The rebuilt root is passed through `collect_infosets`; its consistency check is an acceptance gate.

### Training-state rule

Phase 3 invalidates all solver state after any structural edit. It does not preserve regrets, strategy sums, iteration count, or convergence claims. Warm-start remapping is a documented future optimization because even an unchanged action label may lead to changed continuation payoffs.

Tree editing is atomic: validation builds a candidate root; failure leaves the prior configuration and solution untouched.

## Exact nodelocks

### Data contract

An exact lock maps one `InfoKey` to a complete probability distribution over that information set's legal actions:

```text
locks[info_key][action] = probability
```

Validation requires:

- the key exists and has the declared owner;
- keys in the distribution equal the complete legal action set;
- every probability is finite and in `[0, 1]`;
- probabilities sum to one within a documented numerical tolerance;
- impossible or unreachable keys are rejected during setup rather than ignored.

Phase 3 supports multiple exact locks. It does not support private-hand subsets, bounds, relative-frequency shifts, or partial residual optimization.

### CFR semantics

At a locked information set, every traversal uses the fixed distribution instead of regret matching. Regret updates for the locked owner at that information set are skipped. Strategy sums still accumulate the locked distribution with the same owner-reach weighting as unlocked information sets so exported average strategy reports the constraint exactly.

All other information sets update normally. Chance and reach arithmetic remain identical to the existing synchronous solver.

A lock constrains the modeled game. The resulting strategy is an equilibrium/no-regret solution of that constrained game to the extent supported by the underlying solver and iteration budget. “Minimally exploitative” and “maximally exploitative” are not API guarantees. If the opponent is fully fixed, the unrestricted player should converge toward a best response; if only some opponent information sets are fixed, unfixed information sets continue adapting.

Actual EV is computed with the existing `expected_values` traversal over the exported profile. Lock adherence is checked independently at every locked key.

### Exact oracle

Use a one-step zero-sum matrix game represented as imperfect information:

```text
P0 chooses A or B.
P1 then chooses X or Y without observing P0.
P0 payoff:
        X   Y
A       2  -1
B       0   1
```

Lock P1 to `X:1, Y:0`. P0's unique best response is `A:1`. Lock P1 to `Y:1`; P0's unique best response is `B:1`. These expectations are obtained directly from the payoff table and can be compared with both CFR output and exhaustive pure-strategy best response. A no-lock run is cross-checked against the existing best-response/exploitability code.

Additional tests assert exact exported locked frequencies, unchanged locks over repeated training calls, malformed-distribution rejection, and tree-edit invalidation.

## Player profiles through action incentives

### Contract

A profile assigns a seat a finite incentive coefficient for each supported action category:

```text
check, call, fold, aggressive
```

`aggressive` covers bet and raise. Unknown action kinds fail validation. Coefficients are explicit inputs; Phase 3 does not invent named Fish/Nit/TAG/LAG presets. A documented `maniac_demo` may reproduce the public `aggressive +0.06`, `call +0.03`, `fold -0.06` example, clearly labeled as a product-derived demonstration rather than a calibrated population model.

At a decision with reference pot `P`, choosing category `c` contributes virtual reward

```text
bonus = coefficient[c] * P
```

The reference pot is the matched pot before the action and excludes uncalled excess. Coefficients use an exact decimal/rational input at the API boundary and convert to solver numeric type deliberately.

### Shaped-game solution

Profiles define a shaped behavioral game. A player's shaped terminal utility is:

```text
actual terminal utility + sum(profile bonuses on that player's path)
```

The solver trains against shaped utilities. Implementing this correctly requires carrying accumulated per-player bonuses through traversal or an equivalent exact transformation; adding a bonus to a child value and then returning an unrelated “actual” recursion is invalid.

For the existing two-player solver, the implementation must keep separate value channels or expose a utility wrapper that returns each player's shaped payoff. It must not rely on `-child_value` shortcuts. Profile solving is labeled behavioral modeling, not Nash solving of the original poker game.

After training, reported poker EV is always recomputed from the final strategy using original, unshaped terminal returns. Reports must expose both:

- `actual_ev`: real chip/money utility;
- `profile_objective` or shaped EV: optional diagnostic, clearly labeled virtual.

The virtual bonuses never enter pots, stacks, rake, ICM prizes, or conservation checks.

### Scope

Initial support is seat-wide across the solved tree. Street-specific, node-specific, private-hand-specific, learned, state-dependent, and bet-size-dependent incentives are documented boundaries. The model captures preferences encoded by the coefficients; it is not evidence about a real opponent.

Exact nodelocks take precedence over profile optimization at the same information set: locked policy is used unchanged, while path bonuses may still be accumulated for diagnostic shaped value. This precedence must be explicit in serialized configuration.

### Profile oracle

Use a one-player choice with actual payoffs `check=0`, `call=-1`. With reference pot 10:

- no profile: unique choice is check;
- call coefficient `0.2`: shaped call payoff is `-1 + 2 = 1`, so the unique shaped choice is call;
- exported actual EV under the call policy is `-1`, while shaped EV is `1`.

This fixture proves strategy shaping and EV separation without relying on qualitative poker frequencies. A second two-player matrix fixture verifies that the unprofiled opponent adapts to the profile-shaped policy and that exhaustive enumeration agrees with the bounded solver.

## Serialization and API behavior

A saved configuration includes a schema version, deterministic selectors, exact actions, exact locks, profile coefficients, and precedence. Serialization order is canonical. Loading validates against a freshly built game; stale keys/actions produce a structured error.

Solution metadata records:

- game/configuration fingerprint;
- structural edit set;
- active locks and profiles;
- iteration count and solver mode;
- whether values are actual or shaped.

A solution fingerprint mismatch prevents applying old strategies, locks, or convergence metadata to an edited game.

## Failure tests

Strictly reject:

- selectors resolving to no target or heterogeneous legal decisions;
- edits that create illegal/empty/inconsistent action sets;
- a lock on a physical private-history occurrence instead of a valid `InfoKey`;
- missing/extra actions, NaN/infinite/negative probabilities, or non-unit lock sums;
- stale lock keys after an edit;
- NaN/infinite profile coefficients or unsupported action categories;
- attempts to report shaped value as actual EV;
- attempts to reuse trained state after structural edits.

## Tractability and honest boundary

Map lookup for locks and profile coefficients is constant-time per visited information set/action. The asymptotic traversal remains dominated by the game tree. Validation requires a finite traversal comparable to `collect_infosets`; rebuilding and re-solving are intentionally required after edits.

Implemented target:

- deterministic pre-build tree edits;
- fresh-solver invalidation;
- multiple full-distribution information-set locks;
- seat-wide action-incentive profiles;
- separate shaped training objective and actual EV;
- deterministic serialization and exact toy-game cross-checkers.

Documented boundary:

- live mutation of an in-progress solver;
- safe regret warm starts;
- partial/hand-specific/frequency-bound locks;
- claiming MinES/MaxES or proprietary GTO Wizard behavior;
- named population profiles beyond explicitly sourced demonstrations;
- forward-looking, learned, street/node/size-dependent behavioral models.
